## 2. Контракт с бэкендом (проверено по коду Gateway)

Gateway отдаёт REST на `/api/*` и ходит в микросервисы по gRPC. Ошибки маппятся в ProblemDetails:

| gRPC | HTTP |
|---|---|
| InvalidArgument | 400 |
| Unauthenticated | 401 |
| PermissionDenied | 403 |
| NotFound | 404 |
| AlreadyExists | 409 |
| остальное | 500 (`detail` затирается на «Internal server error occurred.») |

**Роли в JWT совпадают с фронтом** — claim называется ровно `role` (`AppClaimTypes.Role = "role"`), значения `Patient` / `Doctor` / `Receptionist` (`Roles.cs`). `readRole()` работает корректно, проверять не надо.

**Порт Gateway.** В docker-compose Gateway на `5000` (совпадает с дефолтом в `vite.config.ts`), но `launchSettings.json` поднимает его на `5258`. Если запускаешь Gateway из IDE, а не docker — нужен `.env` с `VITE_GATEWAY_URL=http://localhost:5258`, иначе прокси молча ведёт в никуда.

**Чего в Gateway ещё нет** (проксируются через YARP на несуществующие сервисы): `/api/appointments`, `/api/documents`. Значит:

- appointmentsApi писать пока не на что;
- **`photoUrl` во всех create/update-запросах фронт сейчас взять неоткуда.** FileUploader из US (фото профиля, офиса) упирается в Documents API. Это надо заложить в план: компонент грузит файл в `/api/documents`, получает URL, кладёт в `photoUrl`.

**Неудобство контракта, которое сильно повлияет на фронт:** `DoctorListItem`, `DoctorCard`, `ReceptionistListItem` возвращают `specializationId` и `officeId`, а не имена. А US требуют показывать «специализация» и «адрес офиса» в каждой карточке и таблице. Значит любая страница врачей обязана дополнительно тянуть справочники офисов и специализаций и джойнить на клиенте. Об этом — в разделе 4.

## 3. Баги и подводные камни

### 3.1 `useForm` — вся мемоизация мертва (важно)

```ts
export function useForm({ initialValues, validators = {} }) {
  const runValidator = useCallback(..., [validators]);
```

`validators` — объектный литерал, который создаётся заново на каждый рендер вызывающего компонента. Поэтому:

- `runValidator` пересоздаётся каждый рендер;
- за ним — `setValue`, `handleBlur`, `validateAll`, `reset`;
- `isValid` (`useMemo`) пересчитывается каждый рендер, **прогоняя все валидаторы всех полей**;
- любой дочерний компонент, которому передали эти колбэки, теряет смысл `React.memo`.

На форме входа из двух полей незаметно. На «Создать врача» (10 полей) или на модалке записи (7 полей + таблица слотов) — уже нет.

Лечение: положить `validators` в ref и обновлять его в рендере, либо принимать их через `useRef`/фабрику:

```ts
const validatorsRef = useRef(validators);
validatorsRef.current = validators;
const runValidator = useCallback((name, next) => {
  const v = validatorsRef.current[name];
  return v ? v(next[name], next) : null;
}, []); // теперь стабильно
```

### 3.2 `useForm.setValue` — `setState` внутри апдейтера другого `setState`

```ts
setFormValues((previous) => {
  const nextValues = { ...previous, [name]: value };
  setErrors((previousErrors) => { ... });   // ← вызов setState внутри updater
  return nextValues;
});
```

Апдейтер обязан быть чистой функцией. React (особенно StrictMode в dev, и потенциально при конкурентном рендере) может вызвать его дважды — тогда `setErrors` отработает дважды. Сейчас операция идемпотентна, поэтому не стреляет, но это мина. Правильно — один `useReducer` на `{values, errors, touched}`, тогда всё обновляется одной транзакцией и заодно снимается проблема 3.1.

### 3.3 `useAsync` — массив зависимостей переменной длины

```ts
}, [...deps, reloadToken]);
// eslint-disable-next-line react-hooks/exhaustive-deps
```

Если вызывающий передаст массив другой длины между рендерами (например, `[officeId, specializationId].filter(Boolean)`), React сломается или начнёт молча пропускать перезапросы. Плюс `loader` не в deps — гарантированное stale-closure при любом захвате пропсов.

Кроме того, в `useAsync` нет `AbortController`: при поиске врача по имени (US-25, debounce + запрос на каждое изменение) отменённые запросы всё равно долетают до сервера, и порядок ответов не гарантирован — классическая гонка «последний ответ перетирает актуальный». Флаг `cancelled` защищает от записи в state, но не от лишнего трафика и не от того, что более старый ответ придёт последним.

### 3.4 `refreshToken` в `localStorage`

Access-токен в памяти — правильно. А refresh-токен лежит в `localStorage`, то есть достаётся любым XSS. Для медданных это заметный риск. Идеально — httpOnly+Secure+SameSite cookie, которую ставит Gateway (нужна доработка бэка: `/auth/sign-in` кладёт cookie, `/auth/refresh` читает её). Если менять бэк не хочется — хотя бы зафиксируй решение осознанно, это защищаемый компромисс для учебного проекта, но он должен быть выбором, а не случайностью.

### 3.5 Modal — нет focus trap и возврата фокуса

- Tab уводит фокус на страницу под оверлеем — скринридер и клавиатура «проваливаются» сквозь модалку.
- После закрытия фокус не возвращается на кнопку, которая её открыла.
- `Escape` закрывает всегда, даже когда `showCloseButton={false}` и `closeOnOverlayClick={false}` (то есть модалка задумана недизмиссибельной — как `SignInGate`). Нужен отдельный проп `dismissible`.
- `ConfirmDialog` рендерит `Modal` без `title` → `aria-label={undefined}` → диалог без доступного имени.
- Вложенные модалки (модалка создания + ConfirmDialog поверх) оба пишут `document.body.style.overflow`. Сейчас спасает LIFO-порядок размонтирования, но это везение. Надёжнее — счётчик открытых модалок в модуле.

`PasswordInput`: у кнопки-глаза `tabIndex={-1}`, до неё нельзя добраться с клавиатуры. По US это интерактивный элемент — уберите.

### 3.6 Мелочи

- **Нет `.gitignore` в корне `frontend/`** — только внутри двух приложений. Корневой `node_modules` (а он там есть) и `dist` рискуют уехать в гит.
- `index.html` ссылается на `/favicon.svg`, но папки `public/` нет ни в одном приложении → 404 на каждой загрузке.
- Две переменные окружения делают одно дело: `VITE_GATEWAY_URL` (читает `vite.config.ts` для прокси) и `VITE_API_URL` (читает `httpClient`, нигде не задана, поэтому всегда `/api`). В dev работает, в проде `/api` упрётся в статику. Оставь одну и явно опиши поведение для прод-сборки.
- `README.md` в `ClientWebApp` — до сих пор дефолтный шаблон Vite.
- `eslint.config.js` продублирован в двух приложениях слово в слово, а `packages/shared` не линтится вообще (нет скрипта `lint`). Подними один конфиг в корень.
- Нет Prettier — сейчас форматирование ровное, но с ростом кодовой базы разъедется.
- `SignInForm` держит `setTimeout(onSuccess, 1200)` ради показа «You've signed in successfully». Это искусственная задержка; с нормальной системой тостов уведомление живёт само, а модалка закрывается сразу.
- US-1 AC-5 требует нотификацию «Someone already uses this email», а `SignUpForm` на 409 ставит ошибку поля «User with this email already exists». Оба текста есть в `messages.ts` — просто разошлись с ТЗ.
- Нет `ErrorBoundary`: любая ошибка рендера кладёт всё приложение в белый экран.
- Нет тестов и CI. Для проекта такого объёма хотя бы vitest + testing-library на `useForm`, валидаторы и генератор слотов окупятся быстро.

## 4. Производительность

### 4.1 Главное решение — кеш данных (сделать до написания страниц)

Сейчас каждый компонент через `useAsync` тянет данные заново на каждый mount. Учитывая пункт про `specializationId`/`officeId` из раздела 2, страница «Врачи» вынуждена сделать три запроса, и ещё три — когда пользователь ушёл и вернулся.

Два варианта:

**A. TanStack Query** — снимает кеширование, дедупликацию одинаковых запросов, инвалидацию после мутаций, retry и stale-while-revalidate. `useAsync` тогда удаляется. Плюс ~13 KB gzip. Для проекта с таким количеством CRUD-экранов окупается на третьей странице.

**B. Свой `ReferenceDataProvider`** — контекст, который один раз грузит офисы + специализации + категории услуг и отдаёт `Map<id, name>`. Дешевле, но кеш списков врачей/пациентов/записей всё равно придётся писать руками.

Рекомендую A, и поверх него всё равно сделать хук `useReferenceData()` — потому что джойн id → имя понадобится буквально везде (карточки врачей, таблицы, комбобоксы записи).

### 4.2 Разделение бандла

`dist/assets/index-*.js` уже 297 KB на двух страницах-заглушках. Впереди 20+ страниц, датапикер, таблицы, карта офисов (US-23). Без `React.lazy` + `Suspense` по роутам пациент будет грузить весь админский код. Порталу дополнительно логично разделить на doctor-бандл и receptionist-бандл — у них почти не пересекающиеся экраны.

### 4.3 Остальное

- `useDebounce` уже написан, но нигде не используется — он обязателен для всех комбобоксов из US (врач, пациент, специализация, услуга).
- Фото врачей и офисов: сразу договориться про `loading="lazy"` + фиксированный `aspect-ratio` на плейсхолдере, иначе список врачей будет прыгать при загрузке.
- Таблица записей (US-13) может быть длинной — виртуализация не нужна сразу, но пагинацию на сервере лучше обсудить с бэком заранее, чем прикручивать после.
- `AuthProvider.isRestoring` стартует в `true`, и `Navbar` в это время не рендерит кнопки → заметный сдвиг вёрстки при каждой загрузке. Лечится скелетоном фиксированной ширины.

## 5. Визуальная часть

### 5.1 Токены

Что поправить в `tokens.css`:

- **Шкала размеров сломана по смыслу.** `--mmc-font-size-lg: 1rem` — это базовый размер body, а `xl` сразу `1.5rem`. Между ними ничего нет, а заголовки h2/h3 в `Hero` и `Card` уже задают размеры мимо токенов (`2rem`, `1.5rem` хардкодом). Переименуй в честную шкалу: `xs .75 / sm .875 / base 1 / lg 1.125 / xl 1.25 / 2xl 1.5 / 3xl 2`.
- **Цвета мимо токенов:** `#f0f0f0` (Button.white:hover), `#a51f1f` (danger:hover), `#000000` и `#ffffffd7` (AppFooter), `rgba(255,255,255,0.18)` (AppHeader.subtitle), `rgba(255,255,255,0.5)` (AppLayout.role). Каждый такой литерал — место, которое не переключится вместе с темой. Нужны `--mmc-color-primary-dark`, `--mmc-color-danger-hover`, `--mmc-color-footer-bg`, `--mmc-color-on-primary-soft`.
- `--mmc-shadow-md` объявлена и не используется; `--mmc-color-border-strong`, `--mmc-color-warning`, `--mmc-color-primary-active` тоже. Либо примени, либо убери.
- **Тёмная тема** обойдётся почти бесплатно: все компоненты уже читают переменные, достаточно добавить блок `@media (prefers-color-scheme: dark)` с переопределением и снять `color-scheme: light`.
- **Фокус-кольцо `outline: 2px solid var(--mmc-color-primary)` на зелёной кнопке невидимо.** Нужен контрастный цвет + `outline-offset`, либо двойное кольцо (белое внутри, тёмное снаружи).

### 5.2 Чего не хватает в ui-kit под ТЗ

Это самый большой объём предстоящей работы, и его стоит закрыть до страниц — иначе те же контролы напишутся пять раз по-разному:

| Компонент | Где нужен по US |
|---|---|
| `Table` (сортировка, пустое состояние, строка-действие) | US-13, 28, 40, 52, 57, 29 |
| `Combobox` (поиск, фильтрация, «Invalid … name» на blur) | врач, пациент, специализация, услуга — US-6, 64, 25, 50 |
| `Select` / `Dropdown` | офис, статус врача, категория услуги |
| `DatePicker` (+ блокировка дат без слотов, «не позже сегодня») | US-6, 64, 65, 9, 8 |
| `TimeSlotGrid` (шаг 10 мин, 1/2/3 слота под категорию) | Implement time slots generator |
| `Tabs` | US-5 (консультации/диагностика/анализы), US-11 (профиль) |
| `RadioGroup` | статусы Active/Inactive — US-31, 36, 41 |
| `Textarea` | жалобы/заключение/рекомендации — US-58, 59 |
| `FileUploader` | фото профиля и офиса (нужен Documents API) |
| `StatusBadge` | approved/not approved, статусы врача |
| `Toast` + провайдер | все «notification» из AC |
| `Pagination` | списки врачей, пациентов, записей |

`Button` заодно нужны размеры (`sm`/`md`) — в строках таблицы текущий размер с `--mmc-font-size-lg` и паддингом 1.5rem будет громоздким.

### 5.3 Layout

- `PageShell` даёт `max-width: 1120px` — нормально для сайта пациента, тесно для админских таблиц с 6 колонками. Нужен вариант `wide`.
- **В портале нет навигации вообще.** По US там шесть разделов у регистратуры (Appointments, Doctors, Patients, Receptionists, Offices, Specializations) и три у врача. Нужен сайдбар с фильтрацией пунктов по роли — это следующий структурный компонент после ui-kit.
- Адаптив пока сводится к одному медиазапросу в `AppHeader`. Для таблиц надо заранее решить стратегию: горизонтальный скролл или превращение строк в карточки на узких экранах.

## 6. Что я бы делал в таком порядке

1. **Инфраструктура (полдня):** корневой `.gitignore`, Prettier, один eslint-конфиг в корне + линт для `shared`, `public/favicon.svg`, единая env-переменная, `ErrorBoundary`.
2. **Починить `useForm`** (reducer + ref для валидаторов) и **`useAsync`** (стабильный ключ вместо spread, `AbortSignal`) — или сразу заменить `useAsync` на TanStack Query.
3. **Решить вопрос кеша и справочников:** TanStack Query + `useReferenceData` с картами id → имя.
4. **Достроить ui-kit** по таблице из 5.2, начиная с `Table`, `Select`, `Combobox`, `Toast`, `Tabs` — на них завязано больше всего экранов.
5. **Токены и тема:** нормальная шкала шрифтов, вынести хардкод-цвета, видимый фокус, тёмная тема.
6. **Modal:** focus trap, возврат фокуса, `dismissible`, счётчик оверлеев, `aria-label` для `ConfirmDialog`.
7. **Навигация портала** (сайдбар + роли) и роутинг с `React.lazy`.
8. Дальше — страницы: врачи и услуги (публичные, не требуют новых API), затем админские CRUD, затем записи — когда появятся Appointments и Documents API.

Пункты 1–3 стоит закрыть до того, как появится третья страница: чем позже менять `useForm` и слой данных, тем больше экранов придётся переписывать.
